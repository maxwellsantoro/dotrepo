# F-05: autonomous unfamiliar-repository task experiment

Use the [shared boundaries and freeze rules](README.md). Roadmap C1 owns the
freeze and C2 owns this task evaluation; C3 owns later independent participant
use. This experiment can run against the current frozen product while E1 evolves.

## Tasks and causal assignment

Select twelve unfamiliar build/test investigation tasks across at least eight
repositories, with no more than two tasks per repository. Include three tasks
each in Rust, Python, JavaScript/TypeScript and Go, six repository-scope and six
component-scope tasks, and six pre-clone and six local-checkout tasks. These are
marginal quotas, not a fully crossed population sample. Select without evaluated
index access and freeze the roster before inspecting coverage. Retain both direct
coverage and fallback cases when observed; absence of either limits the result.
Each task requires a scope-correct build or test outcome witnessed by its oracle,
not merely a plausible proposed command. Define the intended coverage and useful
completion signal before any agent run.

Pre-clone sessions start with repository identity and task only; they may acquire
source using the same tools and permissions in either arm. Local sessions start
with an identical checkout at the frozen revision. Account for cloning, revision
verification, setup and fallback inside the session when performed by the agent.
Any preparation outside it must be identical across arms, separately costed and
declared; do not prepare the very prerequisite discovery the task is meant to test.

Run three paired repeats per task, two fresh independent sessions per repeat:
72 sessions total. The source-first arm has ordinary upstream/local inspection;
the access arm additionally has the frozen dotrepo integration and snapshot.
Keep task prompt, model, inference configuration, tools, permissions and resource
limits identical apart from dotrepo access and its minimal usage instructions.
Freeze that instruction difference. Source-first sessions cannot reach dotrepo
through another tool, source mirror or search result. No session can read cached
profiles from another run, scorer gold or another session's transcript through
shared storage. Retain access-control checks for both arms.

Randomize which arm executes first within each task/repeat block using a retained
seed and assignment script frozen before execution. Randomize block order too.
Create new workspaces and sessions for every run; reset build, package, HTTP and
application caches to the declared condition, or provision identical frozen
warm caches. Never share a mutable cache between arms. Declare unresettable host
caches and contention; use serialized runs on a reserved host for time claims.

Analyze assignment to access, including sessions that choose not to look up or
immediately fall back. This intention-to-treat comparison prevents selecting only
successful lookup users. Three repeats measure session variation; they do not
turn twelve tasks into 36 independent tasks or 72 independent repositories.

## Required freeze and runner boundary

Before the first session, fix the shared manifest plus:

- Task request, upstream commit, starting state and intended scope; independently
  source-grounded instruction alternatives; task-specific completion oracle and
  error rubric, including incomplete test coverage and incorrect scope.
- Exact provider/model identifier, supported inference settings, full prompts,
  agent/tool runtime, environment/image digest, installed dependencies and network
  permissions. An unpinnable provider model alias limits reproducibility; a
  detected version change interrupts the campaign instead of silently mixing runs.
- Immutable export and retained response hashes, integration/consumer revision,
  identity/age/conflict policy, source-verification requirements and lookup limits.
  Both arms may inspect upstream; the access arm may not query a newer snapshot.
- Equal per-session wall-time, tool-call, token and monetary ceilings; enforced
  stop behavior; campaign-wide budget; retry and outage rules. Freeze actual
  numeric limits before execution. This specification does not launch paid runs.
- Cache state, run order, timestamps, oracle/scorer version, error labels, cost
  rates/date, maintenance allocation denominator and analysis script.

The historical fixed own-project runner checks a selected command against a known
answer before execution. It cannot serve as this autonomous comparison unchanged.
Agents must investigate and decide using only their allowed observations. Keep
gold and completion oracles outside their readable environment; score afterward.
Any runtime refusal must follow the shared permissions and consumer-visible
evidence, never a hidden correct answer. Do not give the access arm an oracle that
silently removes its wrong choices. Score supplied instructions separately from
the agent's own decision to accept them.

Before launch, exercise adapter/exporter and scorer controls, including incorrect
accepted instructions, correct abstention and successful fallback. Existing
[task controls](../../task-fixtures/README.md) and exporter-to-consumer execution
tests provide plumbing checks. The existing scorer expects two alternating runs
per task; randomized repeats need a compatible adapter or revised scorer tested
before freeze. Do not label fixed-runner results autonomous, or coerce randomized
logs into its historical alternating-order contract. Preserve old packets.

## Observation and analysis

Have the scorer assess final artifacts and task errors without arm labels where
practical, then join the assignment and lookup logs. Retain:

| Outcome | Required observation |
| --- | --- |
| Applicable instruction supplied directly | Complete supported tuple from the profile, no upstream discovery fallback; count required source verification separately |
| Correct abstention followed by fallback | Why evidence/acceptance was insufficient, fallback attempted, its effort and whether it succeeded |
| Inapplicable instruction incorrectly accepted | Tuple mismatch and acceptance event, including errors recovered later; distinguish policy selection from agent acceptance |
| Final task completion | Independent task oracle, correctness errors, failed actions, total effort and cost across lookup, verification, setup and fallback |

These outcomes are separate dimensions. A task can receive an applicable profile
instruction and still fail, or complete after a wrong instruction and recovery.
Also retain supported misses, lookup nonuse, timeout, unavailable setup and
unresolved scoring. Every assigned session remains in the outcome ledger.
Budget exhaustion counts as noncompletion. Infrastructure failures remain visible;
apply only the frozen symmetric retry rule, retain original attempts and costs,
and report a sensitivity view instead of deleting unfavorable sessions.

Primary comparison: oracle-passing, correctly completed tasks by assigned arm.
Report incorrect actions and incorrect-instruction acceptance alongside completion;
successful recovery does not erase them. Apply the same applicability/error rubric
to instructions adopted from upstream sources or inferred by either arm. Compare
the fraction of assigned sessions with any incorrect action or any incorrectly
accepted instruction, rather than dividing by lookup hits or accepted answers;
report dotrepo-specific policy selection errors separately. Average paired repeats
within task, then weight tasks equally. Report paired task differences and repository-grouped
results, with scope, ecosystem and pre-clone/local breakdowns. The cohort is
exploratory; report per-task variation and denominators without treating repeat
sessions as independent evidence or claiming population noninferiority.

The leading establishment diagnostic is the fraction of all frozen task sessions
receiving a correctly applicable instruction without upstream discovery fallback.
It is not the experiment's success criterion. Report required source verification
work even for a direct instruction; a raw lookup hit is insufficient.

Report whole-session elapsed time, all tool calls, explicit requests/bytes, actual
provider usage including cached/reasoning tokens where available, failed-call
charges, setup/clone traffic, and allocated preparation/index-maintenance work.
Keep measurement exclusions visible. Missing costs remain null; transferred bytes
are not billed tokens. Present per-use observed cost separately from amortized
shared investigation/maintenance under the frozen allocation; include sensitivity
to reuse rather than choosing an allocation after seeing results.

## Decision and handoff

A complete packet contains all 72 assigned outcomes, retained traces and costs,
protocol deviations and the frozen analysis, even when dotrepo performs worse.
An observed positive completion signal requires higher correct completion with
no higher incorrect-action or incorrect-instruction-acceptance rate. If completion
and error rates tie, fewer total tool calls is an exploratory effort signal;
wall time and costs must still be reported. Conflicting outcomes are a tradeoff,
not an unqualified benefit. Missing maintenance or usage costs preclude a net-cost
claim. These descriptive decision rules justify a larger follow-up, not external
adoption or a statistically established general benefit.

Do not condition this report on E1 passing. Freeze later improved E1 output under
a new experiment identity; reused tasks become a known-workload comparison and
fresh holdouts are needed for a new generalization claim. Independent participant
use, release publication, CI-derived execution evidence and sustained operation
each retain their separate acceptance gates.

## Tooling

From `benchmarks/head-to-head`, use the offline preparation/scoring CLI:

```bash
uv run python -m bench.agent_experiment prepare \
  --manifest /path/to/frozen-manifest.json --out /new/prepared
uv run python -m bench.agent_experiment verify \
  --manifest /path/to/frozen-manifest.json --assignment /new/prepared/assignment.json
uv run python -m bench.agent_experiment summarize \
  --manifest /path/to/frozen-manifest.json --assignment /new/prepared/assignment.json \
  --observations /path/to/observations.json --out /new/report
```

The [module contract](../../bench/agent_experiment.py) defines required manifest
fields and artifact roles; the [synthetic controls](../../../../scripts/tests/test_agent_experiment.py)
include a complete example. Preparation requires actual settings, numeric budgets,
source/model/environment identities and content bindings. It emits 72 requests
with distinct workspace/cache identities and an allowlist excluding gold/oracles.
These identities are declarations for a runner to enforce, not proof of isolation.

Every assigned session needs a retained trace, a post-run score bound to that
trace/oracle/gold/scorer, and a normalized usage receipt. The receipt binds
`sessionId`, `requestSha256`, observed `model`, `environment`, `runtimeSha256` and
the complete `effort` map. Counts/costs must agree with the observation row; unknown
measurements stay null with exclusions. Consistency does not authenticate provider
evidence or independent execution.

The frozen campaign ceiling covers provider cost, preparation and allocated
maintenance cost. A known subtotal above it requires an explicit campaign protocol
deviation and reports `exceeded`; missing costs otherwise leave compliance
`unresolved`. The tool retains all sessions and reports equal-task-weight outcomes
separately from observed arm totals. It does not launch models, run third-party
commands, choose tasks or infer benefit from successful lookups.
