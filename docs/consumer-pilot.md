# Consumer evaluation and pilot preparation

The autonomous consumer evaluation follows the frozen October 29
[F-05 specification](../benchmarks/head-to-head/experiments/applicability-2026-10-29/f05.md)
and its [shared experiment boundaries](../benchmarks/head-to-head/experiments/applicability-2026-10-29/README.md).
F-05 and E1 may proceed concurrently and decide acceptance independently; F-05
execution and reporting do not require E1 to pass. The
[F-05 source roster](../benchmarks/head-to-head/f05-agent-tasks-20261029/README.md)
retains source enrollment and draft gold/oracles; it does not complete the model,
environment, snapshot, budget, scoring, or isolation freeze needed for execution.

External pilot preparation (C3) can start now alongside that work. Its execution
requires participant consent, a separate frozen protocol and a compatible deployed
integration. No participating team, consent, outreach, or independent adoption is
claimed. The internal F-05 campaign and an external pilot retain separate task
rosters, freezes and outcome evidence.

## Historical own-project operator study

The October 4–5 studies below use the maintainer's other public projects. Their
fixed-runner methods and instructions in this section apply to that historical
protocol. Outcomes remain operator evidence; repository ownership and operator
familiarity prevent an independent adoption or generalization claim. F-05 requires
fresh independent agent sessions and post-run scoring under its separate protocol.

Select every substantive other public project before inspecting index coverage.
Exclude dotrepo itself and throwaway canaries by a declared rule. Pin upstream
commits, source-grounded instructions, scope, prerequisites, and completion
oracles before requesting profiles. Keep missing profiles and unavailable setup
in the denominator; do not repair selected records during the frozen comparison.

The [October 4 own-project packet](../benchmarks/head-to-head/results/own-projects-2026-10-04/README.md)
retains the roster, workload, live HTTP receipts, command logs, and scored outcomes.
The fixed runner uses manually selected source instructions. It measures a bounded
reference workflow, not an autonomous model's repository investigation. Explicit
HTTP counts exclude package-manager traffic; bootstrap and preparation costs are
disclosed separately. Unknown model and maintenance costs remain null.

The historical protocol's checkpoint is reviewable paired outcomes and a
disposition for every task. Later fixes receive a new dated run; preserve the
first packet. Useful operator results can justify a later independent pilot,
but do not close its gate.

The [October 5 readiness repeat](../benchmarks/head-to-head/results/own-projects-readiness-2026-10-05/README.md)
retains the same tasks after explicit prerequisite preparation. Its coverage is
already known, and RamenOS uses an identified proposed fix rather than its original
commit. Freeze the revised source pins, environment adapter, time budget, and
snapshot before executing the repeat. This targeted follow-up cannot substitute
for a held-out evaluation. Successful source fallback establishes task readiness;
useful accepted answers and measured task benefit remain separate requirements.
The separate [Atlas SDK follow-ups](../benchmarks/head-to-head/results/own-projects-atlas-scoped-sdk-2026-10-05/README.md)
retain the failed broad selector before the Zig-only environment succeeds with
the complete cohort. Their two-task denominator does not replace the eight-task
repeat, and neither arm accepts an indexed command in these follow-ups.

For another live packet under the historical fixed-runner protocol, require the
controlled Rust-public-export to Python selection and actual execution tests in
`test_contextual_instruction_path.py`.
They cover repository and component instructions without source fallback; they
establish plumbing, not task benefit on the public projects. The repaired runner
constructs profile instructions independently of the expected task answer and
executes the selected instruction only after exact comparison of every context
field. This pre-execution comparison to gold belongs only to that fixed runner;
it must not screen an autonomous agent's choices in F-05 or an autonomous pilot.
Wrong directory, component, prerequisites, or source still requires fallback in
the historical runner. Prerequisites remain descriptions; separately frozen
preparation commands establish its environment.

New freezes of the historical protocol retain SHA-256 bindings and source copies
for all benchmark modules, the dynamically loaded consumer, `pyproject.toml`, and
`uv.lock`. Execution refuses dependency or retained-source changes before HTTP or
task execution. Old packets
remain replayable for scoring but cannot be executed by the changed runner. A new
fixed-runner campaign must also preregister protocol-compatible component paths
and separate operator environment preparation from record instructions:
historical human component labels and SDK environment fields must not be silently
copied into profile answers. Use the merged RamenOS revision and the explicitly prepared
Atlas environment in that new packet; do not amend the readiness packet.

The `contextual-campaign` runner mode keeps the eight source commands and
completion oracles. It uses merged RamenOS `main` and Atlas's merged full-cohort
prerequisite documentation, physical component paths, and an Atlas-only
`preparationEnvironment`. Every expected profile instruction has empty environment
bindings. Execution refuses changes to the frozen Python and `uv` versions before
HTTP or attempt creation. The task request constrains only directory, scope and
component; command/prerequisites still come independently from the profile.
The two RamenOS aggregate host wrappers remain source fallback cases because a
single component context would misstate their multi-component execution. This is
a known-coverage follow-up after bounded source inspection, not held-out evidence.

The [contextual campaign packet](../benchmarks/head-to-head/results/own-projects-contextual-2026-10-05/README.md)
retains eight paired tasks: both arms completed all eight; lookup-first completed
six from actual profile instructions without a source-guide fetch and refused the
two RamenOS aggregates into successful fallback. There were no accepted wrong
answers or failed attempts in that packet. Atlas retained the complete 19-member
cohort and 1,020 vectors per implementation in each correctness arm. This is
observed instruction reuse on source-inspected, prepared operator tasks. Lookup
still made more explicit HTTP requests and received more decoded bytes overall;
warm caches, host contention, unallocated preparation and unknown total costs
prevent a causal timing or net-cost claim. These results do not establish
independent adoption.

## Preparation and handoff

Follow the [roadmap](../ROADMAP.md) for start conditions and priority. Prepare
the external brief, adapter and measurement plan now; consent and the pilot's
execution freeze remain dependencies for collecting participant outcomes:

| Package | Reviewable output | Dependency |
| --- | --- | --- |
| Workload and rubric | Frozen tasks selected before checking index coverage; upstream answers and task-success rubric with source/check dates | No consumer deployment required |
| Integration adapter | Bounded lookup, identity/age/conflict checks, upstream fallback, and outcome telemetry exercised with fixtures | Use the existing [consumer policy](external-consumer-integration.md#positive-command-acceptance) |
| Measurement harness | Independent source-first and access sessions with frozen assignment, cache state, actual usage, fallback work, and maintenance-cost allocation | Validate compatibility and freeze the rubric before execution |
| Recruitment package | Unsent invitation, proposed integration, execution/log ownership, data-handling plan and proposed observation window | Preparation can proceed now; sending requires separate explicit authorization |
| Independent pilot execution | Consenting team, compatible deployed integration URL, frozen workload/protocol and retained outcome report | Participant consent and a complete new pilot freeze; no E1 acceptance gate |

The coordinator fixes the workload and policy versions, checks adapter/harness
compatibility, and integrates the results. Keep unfavorable tasks and unresolved
costs visible. Recruitment preparation does not require a completed E1 or internal
F-05 result. Once consent, deployment and frozen inputs are ready, independent
observations can run alongside internal C2 measurement. Reference runs remain
operator evidence.

The historical task scorer validates workload/log hashes, alternating paired
order, revision/environment, context preservation, and observed completion
separately from policy acceptance.
Its retained controlled runs include accepted wrong instructions and fallback
recovery. Supplied log hashes prove consistency, not independent observation;
operator task oracles and outcomes need review for C2; independent participant
outcomes are required for the C3 outcome gate. Autonomous randomized sessions need
a compatible scorer and assignment contract; do not coerce their logs into the
historical alternating-run format or expose gold through the runtime.

For lookup and command acceptance, use the
[integration contract](external-consumer-integration.md). Record the final task
outcome as well as lookup and fallback results; a 200 response is not task success.

## Pilot design

Agree on and freeze the external pilot's own task list before looking at index
coverage. Use a declared sampling frame and retain selected unindexed repositories
and multiple ecosystems; do not replace tasks to obtain a desired coverage mix.
Freeze model/provider and inference settings, prompts, tools and permissions,
environment/dependencies, cache conditions, immutable snapshot/response bytes,
consumer policy, task oracles, scorer, budgets and cost allocation before execution.
The internal F-05 roster and prescribed session count do not define the external
pilot's workload or sample size.

For an autonomous paired pilot, randomize arm order using a retained assignment
and use fresh independent sessions and isolated workspaces/caches. Keep source
access and resources equal apart from dotrepo access and its minimal instructions.
Keep gold and other sessions' transcripts inaccessible; score actual task outcomes
afterward with the same rubric in both arms. Freeze repeat count, failure/retry
rules and analysis before running; retain errors, abstentions, fallbacks and every
assigned session. Use the [F-05 design](../benchmarks/head-to-head/experiments/applicability-2026-10-29/f05.md)
for these principles, with a separately reviewed external-pilot freeze.

Record HTTP requests, decoded response bytes, wall time, actual model token usage
where available, failed-call charges, setup/fallback work, and allocated preparation
and index maintenance cost. Unknown costs remain null, not zero. Bytes divided by
four is not billed model usage. In the historical
fixed-runner reports, `transport` counts include explicit prefetch and fallback
HTTP work; the own-project runner discloses excluded package-manager/bootstrap
traffic; `elapsedMs` includes the whole arm. Legacy per-field latency excludes
model inference.

## Acceptance

An independent pilot needs a named consenting team, a deployed integration URL,
a stated observation window, a frozen workload, and reproducible outcome data.
Success requires useful answers without a worse incorrect-answer rate and a
measured improvement in the team's chosen latency or cost metric, including
fallback and allocated maintenance. There is no automatic adoption claim based
on reference examples, operator traffic, model interviews, or repository count.

Outreach or submission to another project is a separate explicit action.

Policy-coverage reports measure presence and policy acceptance. They do not
establish correctness or completed tasks; the independently scored workload and
external pilot supply those evidence levels.
